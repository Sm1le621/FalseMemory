# FalseMemory — правила для ИИ-агента

Читай этот файл перед каждой задачей. Правила действуют для всего Unity-проекта.

## 1. Проект и роли

FalseMemory — 2D pixel-art RPG (Dark Fantasy, классический пошаговый бой в стиле JRPG) на Unity 6.

- **Агент:** C#-код, архитектура, интеграция через Unity MCP, исправления, тесты, документация, Git.
- **Владелец:** графика, идеи, геймдизайн, ручное тестирование, окончательные решения. Владелец знает базу C# и ООП, но **не знает Unity** — объясняй Unity-специфику простыми словами.

Работай с существующими системами, не создавай дублирующих реализаций и не трогай посторонние механики. Не удаляй сцены, объекты, Prefabs, спрайты, анимации и пользовательские файлы без разрешения. Перед масштабными или опасными изменениями спроси подтверждение.

Используй Unity MCP (см. `opencode.json`) для Hierarchy, сцен, компонентов, ссылок Inspector, Console и Test Runner. Если действие через MCP недоступно — честно скажи об этом.

## 2. Язык

1. Игровой текст (UI, предметы, заклинания, сообщения, подсказки) — **только английский**. Не смешивай языки в интерфейсе.
2. Текст UI хранится прямо в TMP-компонентах сцен; сообщения боя/инвентаря — строками в коде. Системы локализации (StringTable, `GameText`) в проекте нет — не добавляй без задания.
3. Комментарии в C#-коде — **на украинском** (как в текущих скриптах).
4. Документация и отчёты владельцу — **на русском**. Имена классов, методов, полей и файлов — на английском.
5. Не переименовывай GUID, пути, serialized-поля и ID ради перевода — это ломает ссылки в сценах.

## 3. Стиль кода

1. Простой стиль «уровня 3 курса», как в текущих скриптах: обычные `if`/`else`, простые циклы, понятные имена переменных.
2. Без LINQ, рекурсии, сложных обобщений, «умных» однострочников и лишних паттернов, если задачу можно решить проще.
3. Одна строка — одно действие. Сложную логику дели на маленькие методы.
4. У каждого класса, метода и неочевидного поля — короткий комментарий простыми словами.
5. Не переписывай существующие скрипты «красивее». Сохраняй стиль файла.
6. Соблюдай lifecycle Unity: подписка на события в `OnEnable`, отписка в `OnDisable`; физика в `FixedUpdate`; безопасно проверяй ссылки на `null`.
7. Баланс — через Inspector и ScriptableObject, не хардкодом. Используется новый Input System.
8. Разделяй данные (ScriptableObject), логику (обычные C#-классы) и UI (компоненты, которые только показывают).
9. Никаких QTE и действий на тайминг — бой строго пошаговый. Без платных зависимостей.

## 4. Пиксельные ассеты

1. По умолчанию — нативная сетка **64×64** (персонажи, враги, предметы, простые эффекты); кадр анимации тоже 64×64. Иконки предметов — 32×32. Другой размер обоснуй.
2. Импорт: Sprite 2D, **Point** filtering, без mipmaps и размывающей компрессии, PPU согласован с текущим масштабом.
3. Увеличенное превью — не ассет. Проверяй реальный размер PNG, альфа-канал и вид в игре.
4. Старые ассеты сохраняй; заменяй только разрешённые ссылки.

### Как писать

- Коротко и по делу: таблицы, списки, цепочки вызовов `A → B → C`, фрагменты кода до ~15 строк.
- Читатель знает C# и ООП, но не Unity: каждый Unity-термин при первом появлении объясняй или ссылайся на `01-unity-basics.md`.
- Описывай только то, что реально есть в коде. Будущие возможности помечай явно.
- Числа (характеристики, урон, бонусы) сверяй с ассетами и сценой, а не со значениями по умолчанию в коде.
- **Не создавай:** отдельные файлы на каждый скрипт, Changelog, разделы «История изменений», отчёты этапов, планы, JSON-проверки. История — это `git log`.
- Скриншоты добавляй только актуальные; устаревшие удаляй.

## 6. Проверки перед коммитом

1. Проверь изменённый C#-код и Unity Console (компиляция, ошибки) через MCP.
2. Проверь нужные GameObjects, компоненты и ссылки Inspector.
3. Запусти подходящие тесты (EditMode / PlayMode).
4. Сверь документацию с кодом.
5. По возможности проверь механику в Play Mode.

Не утверждай, что тесты прошли, если не запускал. Не утверждай, что механика работает, если только прочитал код. Не утверждай, что сцена сохранена, без фактического сохранения. Если нужна ручная проверка — дай владельцу короткую инструкцию.

## 7. Git

### Перед задачей
- `git status`, текущая ветка, существующие изменения. Чужие и незавершённые изменения не перезаписывай и не включай в свой коммит.
- Не добавляй `Library/`, `Temp/`, `Obj/`, `Logs/`, `Build*/`, `.vs/`, кеши. Сохраняй `Assets/`, `Packages/`, `ProjectSettings/`, `.meta`, `Docs/`, `AGENTS.md`.
- Никаких токенов, паролей и ключей в коммитах.

### Коммит (после каждой завершённой и проверенной задачи)
1. Добавляй только файлы задачи **по явным путям**; не используй `git add .` при посторонних изменениях.
2. Проверь `git diff --cached`.
3. Сообщение в формате Conventional Commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`. Код и его документация — в одном коммите.
4. Большие задачи — несколькими логическими коммитами. Пустые коммиты не создавай.

### Push — только по явной команде владельца
- Не делай push автоматически.
- Перед push проверь ветку, remote и отправляемые коммиты.
- Push выполняется через **SSH** (`git@github.com:Sm1le621/FalseMemory.git`): HTTPS требует интерактивного логина и в агенте не работает. Ассеты (png/mp3/wav/ttf) хранятся в **Git LFS** — push может быть долгим.
- Проверяй реальный код выхода `git push`, а не код выхода `tail`/пайпа.

Без отдельного разрешения запрещены: `push --force`, переписывание истории, `reset --hard`, `git clean`, удаление веток с изменениями, создание публичных репозиториев, удаление чужих незакоммиченных изменений.

## 8. Отчёт владельцу (на русском, коротко)

- **Что сделано** — результат одной-двумя фразами.
- **Скрипты** — созданные/изменённые и зачем (или «код не менялся»).
- **Unity** — изменённые сцены, объекты, компоненты, ассеты.
- **Документация** — какие файлы `Docs/` обновлены.
- **Проверки** — что реально проверено и чем; что нужно проверить вручную.
- **Git** — ветка, коммит (hash + сообщение), статус push (обычно «не запушено — жду команды»), оставшиеся незакоммиченные изменения.
- **Дальше** — следующий логичный шаг.
