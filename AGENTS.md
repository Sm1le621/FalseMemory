# FalseMemory — постоянные правила разработки, документации и Git

## Classless Character Development Rules

1. FalseMemory использует бесклассовую прокачку: игрок не выбирает и не получает Warrior/Mage/Rogue или другой обязательный класс. Специализация определяется распределением характеристик, экипировкой и изученными способностями.
2. Развивай существующие CharacterAttributes/BattleUnit/Equipment; не создавай параллельную систему персонажа. Сохраняй десять характеристик, стабильные ID и serialized-поля совместимости.
3. Максимум базовой характеристики —99. Эффекты и Scaling используют настраиваемые soft caps; требования предметов проверяются без бонусов самого проверяемого предмета. Не начисляй один Scaling повторно глобальной формулой.
4. AGI влияет на инициативу/уклонение и явно настроенный Scaling предмета, но никогда не повышает скорость ходьбы.
5. Очки характеристик и изучение способностей — независимые ресурсы; повышение максимальных HP/MP само по себе не восстанавливает текущие ресурсы. Классовых ограничений изучения нет.
6. Holy-компонент WIS предназначен только явно отмеченной нежити/нечисти; он не срабатывает на лечение и не порождает повторное применение урона.
7. Актуальные подэтапы5.3–5.7: бесклассовая прокачка/оружие → броня/защита/Holy → изучение способностей → Character по C → баланс/приёмка. Старые предложения обязательных классов являются историей, не текущим заданием.

## Language and Localization Rules

Эти правила действуют для всего текущего проекта и новых заданий:

1. Весь пользовательский игровой контент создаётся на английском (English, en-US): UI, предметы/описания, NPC/ответы, квесты/цели, способности, подсказки и уведомления.
2. Не смешивай русский и английский в игровом интерфейсе. Используй согласованную RPG-терминологию: Inventory, Equipment, Character, Attributes, Attack, Defense, Magic, Items, Quests, Journal, New Game, Settings, Victory, Defeat, Experience.
3. Docs, объяснения скриптов и отчёты владельцу остаются на русском. Названия классов/методов/файлов и игровых терминов сохраняются на английском; их смысл объясняется по-русски.
4. Пользовательский текст хранится централизованно в Unity StringTables, со стабильными ключами; динамические значения передаются параметрами через GameText. Перед завершением каждой новой механики проверь язык текста и границы UI.
5. Не переименовывай технические идентификаторы, GUID, пути, serialized-поля и существующие ID только ради перевода: сохраняй ссылки и будущие сохранения.
6. Новые предметы получают английские имена/описания; новые NPC говорят по-английски; новые задания и игровые сообщения пишутся по-английски. Другие языки добавляются отдельно, только по заданию владельца.

## Pixel Asset Generation Rules

1. Жёсткого ограничения 64×64 нет. Допускаются 32, 64, 96, 128, 192, 256 пикселей и более крупные кадры/листы; размер выбирай по детализации, сцене и качеству, а не ради одного формата.
2. Единый стиль — **Detailed Dark Fantasy Pixel Art**: мрачная атмосфера, сдержанная палитра, читаемые силуэты и согласованное освещение. Утверждённый главный герой — ориентир детализации для персонажей, окружения и VFX.
3. Не уменьшай утверждённую графику до 64×64 без необходимости. Не выдавай искусственное увеличение за новую детализацию; сохраняй реальные исходники и честно указывай размеры.
4. В пределах одной анимации сохраняй одинаковый холст, плотность пикселей и линию стоп. Разные разрешения согласуй через Pixels Per Unit и размер в мире; не растягивай рисунок и не меняй масштаб всей карты ради одного ассета.
5. Импорт: Sprite 2D, подходящая Point filtering, без mipmaps, размытия и потерь от компрессии; настрой slicing, alpha, ground pivot и PPU относительно существующей камеры/коллайдеров. Разрешение не меняет скорость движения.
6. Проверяй фактические размеры, прозрачность, обрезание краёв, границы кадров, масштаб и отображение в мире/бою. Каждый готовый ракурс должен иметь реальные кадры: отражение фронта не является видом сзади. Для отсутствующих ракурсов явно документируй fallback.
7. Старые ассеты, ASE/ASEPRITE, исходные PNG и анимации сохраняй; заменяй только разрешённые ссылки. Новые ресурсы размещай в понятных папках, при перемещении сохраняй GUID/.meta. Подробности — [PixelArtStyleGuide](Docs/Guides/PixelArtStyleGuide.md).
8. Тайлы согласуй с Grid/Cell Size, делай бесшовными и предусматривай края/углы/перекрёстки дорожек. Растения/деревья могут быть крупнее персонажей; учитывай sorting, коллайдеры и камеру. VFX должны иметь настоящие кадры и сохранять читаемость боя без чуждого стилистике 3D.

Прежние правила Git, документации, тестирования и сохранности проекта ниже сохраняют силу.

Эти правила действуют для всего Unity-проекта и всех будущих задач. Перед каждой новой задачей прочитай этот файл. Объяснения, документация и отчёты — на русском языке, понятном человеку без знаний C#.

## Роли и границы работы

FalseMemory — 2D Pixel Art RPG в жанре Dark Fantasy, Unity 6. ИИ отвечает за программирование, техническую архитектуру, интеграцию с Unity MCP, исправления, тестирование, документацию и Git. Владелец отвечает за графику, идеи, дизайн, тестирование игрового процесса и принятие решений.

Работай непосредственно с существующим проектом. Изучай и расширяй имеющиеся системы, не создавай дублирующие реализации без необходимости. Не меняй посторонние механики. Не удаляй пользовательские файлы, сцены, объекты, Prefabs, спрайты и анимации без разрешения. Перед опасными или масштабными изменениями запроси подтверждение. Используй Unity MCP для взаимодействия с редактором, настройки сцен и компонентов, чтения Console и проверки состояния.

## 1. Документация каждого C#-скрипта

При каждом создании, изменении или разрешённом удалении C#-скрипта обязательно обновляй соответствующую документацию. Документация — часть завершения задачи; не спрашивай отдельно, нужно ли обновлять Docs.

Для каждого проектного C#-файла создавай отдельный Markdown-файл в `Docs/Scripts/`. Сохраняй структуру папок: `Assets/Scripts/Battle/BattleManager.cs` → `Docs/Scripts/Battle/BattleManager.md`, `Assets/Tests/...` → `Docs/Scripts/Tests/...`, `Assets/Welcome/...` → `Docs/Scripts/Welcome/...`. При конфликте имён используй подпапки, повторяющие полный относительный путь от Assets, и обнови ссылки, чтобы избежать неоднозначности. Не документируй внешние пакеты как собственную игровую логику.

Каждый документ содержит:

1. **Название и назначение:** имя, полный путь к исходному файлу, задача скрипта в игре.
2. **Как работает:** простая последовательность действий и условия их выполнения.
3. **Методы и функции:** для каждого значимого метода — название, момент вызова, назначение, входные данные, возвращаемое значение или изменяемое состояние, связь с другими методами. Отдельно объясняй присутствующие Unity-методы Awake, Start, Update, FixedUpdate, LateUpdate, обработчики столкновений и остальные callbacks.
4. **Переменные и Inspector:** имена, назначение, допустимые значения и влияние на игру. Отличай значения по умолчанию в коде от назначенных значений сцены/ассета. Не выдавай внутреннее состояние за редактируемый параметр.
5. **Связи:** необходимые компоненты, вызываемые скрипты, используемые GameObjects, события и ссылки Inspector.
6. **Пример:** практическая последовательность из FalseMemory.
7. **Настройка в Unity:** к какому GameObject прикреплять, какие компоненты нужны, какие ссылки назначать и какие параметры менять. Для статического класса или теста явно укажи, что компонент не прикрепляется; для ScriptableObject объясни создание/назначение ассета.
8. **Возможные проблемы:** типичные ошибки, необходимые настройки Unity, конфликты, ограничения и способы устранения.
9. **История изменений:** дополняй значимыми датированными записями, не переписывай прежнюю историю. Не придумывай события и даты; первичная документация описывает прочитанный текущий код.

Если скрипт удаляется с разрешения владельца, обнови, архивируй или удали его документацию с учётом истории Git.

## 2. Документация систем

Веди документы существующих игровых систем в `Docs/Systems/`: например CombatSystem, HealthSystem, MagicSystem, InventorySystem, EnemyAISystem. Создавай документ при появлении соответствующей системы. Не описывай отсутствующие механики как реализованные; будущие возможности отмечай явно.

Каждый документ включает назначение, общую логику, основные компоненты, взаимодействие скриптов, последовательность событий, настраиваемые параметры, инструкцию использования в Unity, способы расширения и известные ограничения. При существенных архитектурных изменениях автоматически обновляй соответствующие документы.

## 3. Общая документация

Поддерживай:

- `Docs/README.md` — главный указатель со ссылками на все игровые системы и отдельные описания скриптов.
- `Docs/Architecture.md` — фактическая архитектура, структура папок, основные системы и связи.

Документация должна соответствовать реальному текущему коду и настройкам Unity. Указывай, что проверено поведением в игре, что автоматическими тестами, а что только чтением кода. При сохранённых незакоммиченных изменениях поясняй, что документируется рабочая копия, а не только HEAD.

## 4. Git перед каждой задачей

1. Выполни `git status`, определи текущую ветку и проверь индекс/существующие изменения.
2. Убедись, что чужие и незавершённые изменения не будут перезаписаны или случайно включены в коммит.
3. Проверь Unity `.gitignore`. Не добавляй автоматически генерируемые Library/, Temp/, Obj/, Logs/, Build/, Builds/, .vs/, локальные кеши и временные файлы.
4. Сохраняй Assets/, Packages/, ProjectSettings/, необходимые Unity `.meta`, Docs/ и AGENTS.md. Не исключай все `.meta`.
5. Не добавляй токены, пароли, API-ключи и другие секреты.

Если локального репозитория нет, разрешено создать его через git init, проверив папку и `.gitignore`; сообщи результат. Не создавай удалённый репозиторий без разрешения. Не удаляй уже отслеживаемые файлы только из-за нового `.gitignore`: сначала оцени последствия и сохранность данных.

## 5. Автоматический локальный коммит

После каждого успешно завершённого и проверенного задания выполняй локальный непустой коммит:

1. Проверь `git status` и `git diff`.
2. Обнови относящуюся к задаче документацию.
3. Добавь в индекс только файлы текущего задания по явным путям. Не используй бездумно `git add .` при наличии посторонних изменений.
4. Проверь `git diff --cached`: никаких случайных файлов, секретов и посторонних изменений.
5. Создай коммит с сообщением Conventional Commits, соответствующим фактическому результату:
   - `feat:` — новая механика;
   - `fix:` — исправление;
   - `refactor:` — изменение структуры без изменения поведения;
   - `docs:` — документация;
   - `test:` — тесты;
   - `chore:` — технические изменения.

Примеры: `feat: implement magic and MP`, `fix: correct player health UI`, `docs: document combat system`. Связанные реализацию и документацию одной законченной задачи включай в один коммит. Не создавай пустые коммиты. Если есть критические ошибки, сначала сообщи и исправь их; не выдавай задачу за готовую и не создавай автоматически коммит с пометкой готовности.

Для больших новых заданий сохраняй завершённые и проверенные подэтапы отдельными логическими коммитами. Не включай ранее подготовленные чужие изменения. Если user.name/user.email отсутствуют, сообщи об этом; не придумывай личность владельца.

## 6. Push — только по явной команде владельца

Самостоятельно разрешены безопасное чтение Git, status, diff, log, просмотр веток, add и локальный commit. **Не выполняй push без явной команды пользователя.** Не делай push автоматически после коммита.

По команде «Сделай git push» проверь текущую ветку, настроенный remote, локальные коммиты и отправляемые файлы на секреты/посторонние изменения. Выполни обычный push в однозначно определённую удалённую ветку и сообщи результат. Если remote или цель неоднозначны — уточни. При ошибке объясни её; не применяй опасные обходные способы без разрешения.

Без отдельного разрешения запрещены:

- `git push --force` и любые формы принудительного push;
- переписывание истории коммитов;
- разрушительные `git reset --hard` и `git clean`;
- удаление веток с изменениями;
- автоматическое создание публичного GitHub-репозитория;
- удаление чужих незакоммиченных изменений.

Не меняй основные правила документации, локальных коммитов и запрета push без разрешения владельца. Если последующая инструкция противоречит этим правилам и затрагивает безопасность Git или сохранность данных — запроси уточнение.

## 7. Автоматическое сопровождение изменений

При новой механике, исправлении, создании скрипта, изменении системы или архитектуры, добавлении врага, оружия, предмета или заклинания самостоятельно определяй нужные обновления Docs/Scripts, Docs/Systems, Architecture, README и Changelog. Не дублируй бессмысленно правила в нескольких местах; вспомогательные документы могут ссылаться сюда.

## 8. Проверки до коммита

1. Проверь относящийся к задаче C#-код.
2. Прочитай Unity Console через MCP и проверь завершение компиляции/ошибки.
3. Проверь необходимые GameObjects, компоненты и связи.
4. Запусти доступные подходящие автоматические тесты и изучи результаты.
5. Проверь соответствие документации коду.
6. По возможности проверь связанную механику в Play Mode.
7. Если ручная проверка обязательна или автоматическая недоступна — явно объясни ограничение и дай конкретные инструкции владельцу.

Не утверждай, что тесты прошли, если их не запускал. Не утверждай, что механика работает, если прочитан только её код. Не утверждай, что сцена сохранена, без фактического сохранения. Исторические результаты отделяй от проверок текущей задачи.

## 9. Итоговый отчёт каждой задачи

Отчёт на русском включает:

- **Выполненная задача:** краткий результат.
- **Созданные и изменённые скрипты:** список и простое объяснение назначения; явно укажи отсутствие изменений кода, если это так.
- **Изменения в Unity:** объекты, компоненты, сцены, Prefabs и настройки либо отсутствие изменений.
- **Документация:** новые/обновлённые документы.
- **Проверки:** реально выполненные действия, результаты, ограничения и ручные проверки.
- **Git:** ветка, включённые файлы и их количество, сообщение коммита, короткий hash, статус push. Обычно: `Not pushed — waiting for user command`. Отдельно укажи оставшиеся незакоммиченные изменения.
- **Следующий этап:** следующий логичный шаг разработки.

## 10. Первоначальная настройка документации

Первоначальная задача (выполняется один раз, не повторяется перед каждой задачей): проверить Git и `.gitignore`, создать этот файл и структуру Docs, прочитать существующие проектные C#-скрипты, создать отдельные описания, README, Architecture, документы существующих систем и Changelog; проверить соответствие коду и изменения Git; при отсутствии блокирующих проблем сделать локальный коммит только правил и документации. Push не выполнять.

Временные задания, включая конкретный этап боевой системы, не превращай в постоянное требование повторной реализации. Изучай существующий результат и продолжай с фактически незавершённого места.

## 11. Качество кода и архитектуры

Используй понятные имена, избегай дублирования и ненужных глобальных менеджеров. Сохраняй подходящую существующую архитектуру. Отделяй данные, логику и UI там, где это оправдано задачей, без несогласованного масштабного переписывания. Настраивай баланс через Inspector/ScriptableObject. Соблюдай lifecycle Unity, предпочитай события лишним Update, безопасно обрабатывай отсутствующие ссылки. Учитывай установленный Input System. Не добавляй платные зависимости, QTE и боевые действия по таймингу: цель — классическая пошаговая RPG.

## 12. Рабочий процесс

Анализ актуального кода/Docs/Unity/Git → план необходимых изменений → реализация → проверка компиляции/Console/компонентов/тестов → документация → адресный add/проверка индекса/локальный commit → отчёт → следующий разрешённый подэтап. Продолжай самостоятельно, если предыдущий проверен и ручная проверка не требуется для надёжного продолжения. Иначе остановись с конкретной короткой инструкцией владельцу.
